Module Generator v2

Generador de modulos completos para el ERP LWM. A partir de un archivo JSON de configuracion, genera todos los archivos necesarios para un modulo funcional con CRUD completo, tests, permisos y autorizacion.

El generador produce codigo que cumple los estandares del proyecto sin necesidad de edicion post-generacion.

Que genera?

Por cada entidad en la configuracion:

ArchivoDescripcion
MigrationTabla con columnas, FK, indices
ModelEloquent con fillable, casts, relaciones, LogsActivity
SchemaJSON:API schema con fields, filters, includePaths, pagination
Authorizer10 metodos con permisos $user->can()
RequestValidacion con required/sometimes, unique ignore, toOne
ControllerJSON:API controller con Actions traits
FactoryFactory con faker apropiado por tipo
5 TestsIndex, Show, Store, Update, Destroy (CRUD completo)

A nivel de modulo:

ArchivoDescripcion
jsonapi.phpRutas JSON:API con relaciones
RouteServiceProviderProvider de rutas del modulo
PermissionSeederCreacion bulk de permisos (5 por entidad)
AssignPermissionsSeederAsignacion de permisos por rol
DatabaseSeederSeeder principal del modulo

Comando

php artisan module:generate NombreModulo --config=ruta/config.json

Pasos post-generacion

php artisan migrate
php artisan test Modules/NombreModulo/
# Revisar TODOs en el codigo generado para logica de negocio

Estructura del JSON de Configuracion

El archivo JSON tiene dos niveles: modulo y entidades.

Estructura raiz

{
  "module": "NombreModulo",   // PascalCase, requerido
  "entities": {
    "Entidad1": { ... },      // PascalCase, al menos 1
    "Entidad2": { ... }
  }
}
module debe coincidir exactamente con el argumento del comando: php artisan module:generate NombreModulo

Estructura de entidad

{
  "NombreEntidad": {
    "table": "nombre_tabla",     // Opcional, snake_case plural auto-generado
    "fields": [ ... ],           // Requerido, al menos 1 campo
    "relationships": [ ... ]     // Opcional
  }
}

Estructura de campo

{
  "name": "nombre_columna",    // Requerido, snake_case
  "type": "string",            // Requerido (ver Tipos de Campo)
  "rules": "required|max:100", // Opcional, pipe-delimited
  "default": "valor",          // Opcional, cualquier tipo JSON
  "sortable": true,            // Opcional, default false
  "filterable": true           // Opcional, default false
}

Estructura de relacion

// Relacion al mismo modulo:
{
  "type": "belongsTo",       // belongsTo | hasMany | hasOne
  "model": "OtraEntidad",    // PascalCase
  "entity": "OtraEntidad"    // Indica que esta en el mismo modulo
}

// Relacion a otro modulo:
{
  "type": "belongsTo",
  "model": "Contact",
  "module": "Contacts"       // Modulo externo
}
Cada relacion debe tener entity (mismo modulo) O module (otro modulo), nunca ambos ni ninguno.

Cada tipo genera automaticamente la columna de migracion, cast del modelo, campo del schema, faker para factory y valor de test.

Para enum, usa la regla in:val1,val2,val3 para definir los valores permitidos. El faker generara randomElement() con esos valores.
Para string, si incluyes max:N en las reglas, la migracion usara string(N) en vez del default 255.

Relaciones

belongsTo (N:1)

La entidad tiene la FK. Se genera automaticamente:

  • Columna FK en migracion: snake_case(Model)_id
  • Constraint ->constrained()->onDelete('restrict')
  • Metodo belongsTo() en modelo
  • BelongsTo::make() en schema
  • JsonApiRule::toOne() en request
  • Soporte nullable con la propiedad "nullable": true
// Una orden pertenece a un contacto (modulo externo)
{ "type": "belongsTo", "model": "Contact", "module": "Contacts" }

// Un item pertenece a su orden (mismo modulo)
{ "type": "belongsTo", "model": "Order", "entity": "Order" }

// FK nullable
{ "type": "belongsTo", "model": "Warehouse", "module": "Inventory", "nullable": true }

hasMany (1:N)

La entidad no tiene FK (la tiene el hijo). Solo genera la relacion en modelo y schema.

// Una orden tiene muchos items
{ "type": "hasMany", "model": "OrderItem", "entity": "OrderItem" }

hasOne (1:1)

Igual que hasMany pero para relaciones uno-a-uno.

{ "type": "hasOne", "model": "Warranty", "entity": "Warranty" }

Dependencia entre entidades

El generador ordena automaticamente las entidades por dependencia para que las migraciones se creen en el orden correcto. No necesitas preocuparte por el orden en el JSON.

Reglas de Validacion

Las reglas se escriben en formato pipe-delimited (ej: required|string|max:100).

Combinaciones comunes

"rules": "required|string|max:100"            // Texto corto obligatorio
"rules": "required|unique|string|max:50"       // Codigo unico (SKU, folio)
"rules": "nullable|numeric|min:0"              // Numero opcional positivo
"rules": "required|in:pending,active,closed"   // Enum obligatorio
"rules": "required|boolean"                    // Boolean obligatorio
"rules": "nullable|date"                       // Fecha opcional
"rules": "nullable|array"                      // JSON opcional

Permisos por Rol

El generador crea 5 permisos por entidad y los asigna segun el rol:

RolPermisosDescripcion
godTodos (wildcard query)Acceso total
adminindex, show, store, update, destroyCRUD completo
techindex, showSolo lectura
customerindex, showSolo lectura
guestNingunoSin acceso (401)

Formato de permisos

// Para entidad ShipmentItem -> jsonApiType = shipment-items
shipment-items.index
shipment-items.show
shipment-items.store

Los permisos se crean con BulkPermissions trait usando insertOrIgnore para eficiencia.
